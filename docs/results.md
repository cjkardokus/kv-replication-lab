## Why these results look the way they do

### `ack_required=0` has high staleness, high failures, and much higher elapsed time than every other leader-follower config

This is expected, not a bug -- `ack_required=0` is fire-and-forget: the write path never awaits any follower before returning, so there is zero backpressure on how fast writes can be issued. Under this benchmark's sustained, unthrottled load, that has two real, compounding consequences:

- **Every value is real, but the ranking reflects a genuine trade-off, not a measurement error.** `ack_required=1..4` show a clean monotonic staleness staircase (roughly 22% &rarr; 10% &rarr; 4% &rarr; 1% as `ack_required` rises) with zero internal exceptions logged on the leader -- awaiting even one real ack naturally bounds how many replicate calls can be in flight at once (bounded by how many client writes are concurrently in flight).
- **`ack_required=0` has no such bound.** A large connection pool (`leader_follower/leader.py`'s `_CLIENT_MAX_CONNECTIONS`) avoids silently dropping replicated writes to `httpx.PoolTimeout`, but doesn't fix the underlying lack of backpressure: under sustained load the followers (plain uvicorn, no concurrency limiting of their own) get more concurrent replicate traffic than they can drain, which keeps each replicate call alive longer, which lets yet more unthrottled writes pile up before the old ones finish -- a feedback loop that eventually starves the *leader's own* event loop badly enough to time out on its own trivial, in-memory-only client-facing PUT endpoint. See `leader_follower/leader.py`'s `_CLIENT_MAX_CONNECTIONS` comment for the full investigation and exact failure counts.

Fixing this for real would mean bounding *concurrent in-flight replicate fan-out* independently of connection-pool size (e.g. a semaphore in `Replicator`) -- a deliberate follow-up, left undone for now by design, since it changes `ack_required=0`'s fire-and-forget semantics rather than just re-tuning a constant.

### Every leaderless config shows 0.00% staleness, including the `W=2,R=3` boundary case meant to demonstrate measurable staleness

Four of the five are legitimately guaranteed or effectively guaranteed, not a finding:

- `W=1,R=5`, `W=5,R=1`, `W=3,R=3`: guaranteed by the classic W+R>N overlap rule (or one side already equals N).
- `W=1,R=1`: not guaranteed by the rule, but this implementation's write path unconditionally background-replicates a W=1 write to *every* node, and that finishes in low single-digit milliseconds on localhost -- far faster than the ~250-330ms average gap between requests touching the same key at this benchmark's throughput (10,000 requests / 100 keys). The race window that would expose staleness is real but too narrow to hit reliably on one machine's loopback interface -- the same category of local-testing blind spot this project's README already documents for clock skew. See the top of `experiments/leaderless_staleness_load_test.py` for the full writeup and what it would take to reproduce locally.

`W=2,R=3` deliberately sits *on* the W+R=N boundary and was expected to show measurable staleness -- it doesn't, and that's a real, investigated characteristic of this implementation: `QuorumCoordinator`'s `_FANOUT_MARGIN` (a resilience feature, contacting one extra peer beyond the bare minimum so one slow/unreachable peer can't fail quorum by itself) pads effective coverage at this cluster's size (N=5) enough that a W=2 write's 3-of-5 node coverage and an R=3 read's 3-of-5 decisive set are mathematically guaranteed to overlap by pigeonhole (3+3-5=1) whenever every contacted peer succeeds -- which they did for every write in this run (0 leaderless failures). This holds regardless of whether coordinator selection is round-robin or random -- it's a property of the *set sizes* the margin produces, not of which specific nodes get picked. See `leaderless/node.py`'s `_FANOUT_MARGIN` comment for the full derivation. No change has been made here -- shrinking the margin would make the boundary case demonstrable but weakens real resilience, a deliberate trade-off left for a follow-up rather than done incidentally.
